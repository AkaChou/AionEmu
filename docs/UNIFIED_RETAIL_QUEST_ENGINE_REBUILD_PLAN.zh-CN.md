## 路线纠正（2026-08-02，覆盖此前批量候选路线）

**不再把 Python 生成器当作“语义转换器”一次性转换 6167 个 owner。** 它擅长统计、抽取候选和闭包校验，却无法可靠理解复杂 Handler 的控制流、对话协议、AI 生命周期、实例对象和失败语义。此前 owner 级“一条 path 不确定就丢弃整个 owner”正是这一错误的产物（5600 个 unresolved）。

新路线：

```
机制盘点 → 补通用 typed block → 代表任务纵向验证 → 冻结能力层
  → 每次选择一个 owner（或已证明同构的小族）→ Python 单 owner 辅助 → 人工完成 XML/DSL
  → shadow 验证 → 最后统一切换生产 owner
```

- **能力优先**：从全量 Handler inventory 找高频机制，选真实代表任务，追踪完整事件与副作用，抽象为通用 typed block，同时实现 IR/DSL/XML/compiler/runtime port。能力只有经真实任务端到端跑通才算完成。
- **代表任务验证**：每类能力至少一个真实任务，高风险能力用两个不同任务验证，避免把任务特例错误抽象成通用能力。
- **冻结能力层**：能力稳定后，转换普通任务只允许新增 XML/DSL 定义、fixture、manifest 和审计报告，不得再改 IR/XSD/compiler/runtime/DAO/central executor。
- **逐任务迁移**：按任务族、按 owner 逐个转换，每个 owner 单独证明所有可达路径和副作用闭包，`replacement_ready=true` 前不得接管生产。
- **Python 降级为辅助工具**：全量模式只允许 inventory、能力频率、注册事件/常量抽取、path/unresolved 统计和差异报告；定义投影必须显式指定一个 quest ID。Python 不得批量输出可导入定义、不得生成生产/candidate manifest、不得把投影计为 executable/migrated owner。
- 单 owner 投影只能标记 `ANALYSIS_DRAFT`，默认 `reviewed=false/verified=false/replacement_ready=false`；`QuestDefinitionCandidateImporter` 与 `ImmutableQuestCatalog` 都拒绝该所有权。人工复核所有可达路径后，必须把最终 XML/Java DSL 作为独立源码重新提交并用代表任务、运行时与 shadow 证据晋级。
- XML 与 Java DSL 仍必须编译为同一不可变强类型 IR；DSL 仍只是声明式定义，禁止 callback、服务调用和旧 Handler 逻辑。
- 任务复杂度决定载体：数据化规则固定优先 XML；分支较多仍由 typed block 表达用 Java DSL；两者最终编译为同一 IR。

**本轮（2026-08-01 起）执行顺序**：更新本文档 → 重跑 inventory/owner/path 基线 → 建立 capability acceptance matrix → Python 降级 → 补齐对话/状态/物品/奖励/启动/完成 typed block → 传送 → 刷怪/despawn → 影片/MovieEnded → AI 命令/回调 → 任务 timer/invisible timer → 剩余 required mechanism → 每类能力代表任务转换与验证 → 冻结能力层 → 第一个任务族逐 owner 转换 → 保持所有生产 owner 不变 → 汇总下一批可安全转换任务族。

`production_owner_switch=0` 始终是安全约束，不是缺陷。

## 目标

在当前 `quest/main` 基线重建统一任务引擎：由不可变的 `QuestDefinition` 同时承载任务元数据与流程，统一 XML 与 Java DSL 的编译结果，并以可验证、可回滚、证据驱动的方式替代 `quest_data`、旧可执行 XML 和 Java Handler。

`new`、`history` 只用于提取能力清单、失败案例和测试思路，禁止恢复或合并其运行时实现。

## 不可违反的约束

- 迁移顺序固定为：当前实现与真端能力并集盘点 → 通用基础设施闭包 → 代表任务验证并冻结能力 → 逐 owner 人工转换 → 全局门禁 → 按已验证范围切换 → 逐任务真端校准。不存在“全部当前任务机械迁移”阶段。
- 禁止任意服务调用、反射、字符串表达式、任务专属 executor、空处理器、静默 fallback 和 per-quest Java lambda。
- 节点只作为编译期标签；运行时状态只能投影到 `QuestStatus + quest_vars`，不建立 graph node 状态表。
- 位域只能使用现有 32-bit `quest_vars`，声明必须有 offset、width、范围和持久化模式；越界、重叠或无证据布局必须编译失败。
- `QuestCatalog` 是唯一任务目录接口；最终退役 `QuestTemplate`、`QuestsData`、`DataManager.QUEST_DATA` 和旧 `quest_data` 加载链，不保留双源兼容 facade。
- 当前没有执行 owner 的条目标记 `CATALOG_ONLY`，不得伪造空流程。
- 外部 AI、副本、世界和队伍逻辑只能通过类型化 `QuestEventPort`、只读事实快照和 `QuestActionPort` 交互，禁止直接写 `QuestState`。
- 所有 required 动作必须在单一 `QuestUnitOfWork` 数据库事务中完成；失败整体回滚，且不得执行 `afterCommit`。
- 关键领域效果必须由所属领域端口幂等、持久接管并可恢复；无可靠端口时能力保持阻断。
- 未完成 full dry-run、shadow 和全局门禁前，`production_owner_switch=0`。
- 真端证据不足时保留当前定义并标记 `CURRENT_FALLBACK/UNRESOLVED`，不得猜测或宣称 `RETAIL_ALIGNED`。

### 真端能力边界

- `fun_912.cpp:668-737` 是类型分派闭包，允许的真端类型只有 `talk`、`hunt`、`collect`、`use_item`、`item_play`、`serial_hunt`；候选 XML 出现其他类型时必须 `UNMAPPED` 并阻断导入。
- `fun_912.cpp:742-804` 的公共初始化会根据类型选择完成状态/奖励路径，并通过事件总线登记任务对象；该函数只能作为执行语义证据，不能推断 Java 侧事务或客户端包。
- `QuestDB.cpp:221-307`、`419-472`、`481-540` 证明真端加载器按 root 和 `id` 建立全局任务表，重复 ID 是错误；它还把 `talk_npc1` 的存在映射到不同进度类型。
- `SimpleHuntQuest.cpp` 与 `SimpleSerialHuntQuest.cpp` 的恢复代码只证明对象创建、目标分组和事件登记，不足以证明奖励、库存、队伍 credit、cleanup 或 after-commit 语义；这些字段保留 `CURRENT_FALLBACK/UNRESOLVED`。
