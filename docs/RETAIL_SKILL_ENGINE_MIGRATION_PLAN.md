# 真端技能数据接入技术方案

> 当前状态（2026-07-15）：技能模板已迁入 `definitions/compact/skills/`，当前权威索引包含 14,517 条模板；14,457 是技能分类数量。本文其余 14,494 等数量属于上一版 V3 审计快照，保留为字段语义与运行验收依据。

## 1. 结论

采用“真端数据编译适配层”方案，不重写现有技能引擎，也不整体移植 `aion-server` 技能引擎。

运行时数据流如下：

```text
definitions/compact/skills/index.xml（权威索引）
        │
        ├── groups.xml（公共结构与字段字典）
        └── skill_templates_part_001.xml ... part_029.xml
        │
        ▼
SkillDefinitionLoader（展开公共结构与真端字段）
        │
        ▼
现有 SkillData / SkillTemplate
        │
        ▼
现有技能引擎、AI、控制器、封包和脚本
```

该方案把改动限制在静态数据加载边界，继续复用现有 `SkillTemplate` 模型、效果实现和所有技能调用方。`compact/skills/index.xml` 及其列出的 29 个分片是运行时唯一权威源，不再生成或读取第二份技能模板缓存。

## 2. 目标与非目标

### 2.1 目标

- 让 `definitions/compact/skills/index.xml` 列出的真端转换分片成为运行时技能模板的权威来源。
- 完整加载真端的 14,494 个技能，不因当前模板缺少对应字段而静默丢弃数据。
- 保持 `DataManager.SKILL_DATA`、`SkillData` 和 `SkillTemplate` 对上层调用方的接口稳定。
- 将真端字段、效果类型及 `reserved` 参数转换为现有引擎可执行的模板结构。
- 保证技能模板分片与同目录 `npc-skills.xml` 的技能 ID、子技能及其他关联引用完整。
- 在切换前生成可审计的旧数据/真端数据差异报告，所有差异必须有明确解释。
- 编译失败、未知效果或引用缺失时启动失败，禁止悄悄使用旧技能数据兜底。

### 2.2 非目标

- 不整体重写技能施放、命中、伤害、效果生命周期和封包流程。
- 不整体复制 `/Users/mc/IdeaProjects/aion-server` 的技能引擎。
- 不把 357 个真端原始字段直接塞入现有 `SkillTemplate`。
- 不在本阶段顺便统一战斗公式、重构所有效果类或清理历史 XML。
- 不把字段或关联闭包不完整的模板写入 `definitions`。

## 4. 为什么不直接使用 `aion-server` 技能引擎

`/Users/mc/IdeaProjects/aion-server` 可用作语义参考，但不能直接替换当前引擎：

|---|---:|---:|

| 效果类 | 197 | 191 |
| 同路径文件 | 257 | 257 |

| 缺少真端技能 | 84 | 1,457 |

- 少数缺失或改名的效果实现；
- 已转换模板，用于反推 `reserved` 参数含义。

每项复用都必须按技能样本验证，不能以“另一个服务端这样写”为唯一依据。

## 5. 数据边界与模块设计

### 5.1 权威数据

- 权威索引：`definitions/compact/skills/index.xml`。
- 权威模板：索引列出的 `skill_templates_part_001.xml`～`skill_templates_part_029.xml`。
- 公共结构：同目录 `groups.xml`。
- 关联权威输入：同目录 `npc-skills.xml`、`skill-categories.xml`、`motion_times.xml` 和 `charge_skills.xml`。
- 外部 `converted_staticdata_v3` 仅作为生成来源，不参与运行时读取。
- 旧模板仅用于差异对照，不参与正式运行时合并。

### 5.2 最小加载组件

当前只使用一个 `SkillDefinitionLoader`：读取索引、展开 `groups.xml` 公共结构和真端字段，再由 JAXB 构造现有 `SkillData`。数量与引用闭包由加载器和聚焦测试校验，不新增第二套运行时技能仓库、编译缓存或平行技能模型。

### 5.3 启动接入点

接入 `XmlDataLoader` 的技能加载步骤：

```text
读取 definitions/compact/skills/index.xml
  → 读取 groups.xml 字段字典与公共结构
  → 按索引顺序展开 29 个模板分片
  → 校验模板总数为 14,494
  → 构造 SkillData 并建立 ID、技能组、冷却组索引
  → 加载同目录 NpcSkillData
  → 发布到 DataManager
```

任一索引、公共组、分片或数量校验失败都会中止静态数据加载，不会回退到已删除的旧 `skill_templates.xml`。

## 6. 真端数据编译规则

### 6.1 sparse table 解码

compact XML 使用字段字典与稀疏值表，解析器必须：

- 先建立字段编号到稳定字段名的映射；
- 区分“字段缺失”“空字符串”“零值”和显式默认值；
- 保留原始字符串和值来源，便于差异报告定位；
- 拒绝重复技能 ID、未知字段编号和非法字段类型；
- 对字段字典计算摘要，避免转换器升级后误用旧缓存。

解析层不解释技能业务。这样可以分别测试“原始数据是否无损”和“业务语义是否正确”。

### 6.2 357 个字段的分类

所有字段必须进入且只能进入以下一类：

| 分类 | 处理方式 | 示例 |
|---|---|---|
| 模板直接字段 | 映射到现有 `SkillTemplate` 属性 | ID、等级、冷却、施法时间 |
| 结构字段 | 组合为现有嵌套模型 | `properties`、`actions`、`motion` |
| effect 字段 | 交给 effect 编译器 | `effectN_type`、`effectN_reservedM` |
| 关联字段 | 解析并校验外键 | 子技能、motion、文本、charge set |
| 仅客户端字段 | 保留在报告，不进入服务端模板 | 纯显示资源字段 |
| 已证明无运行意义 | 显式忽略并记录依据 | 真端未使用的保留字段 |
| 未知字段 | 阻止切换 | 尚无可靠语义的字段 |

“字段存在但当前引擎不用”不等于可以忽略。只有通过 58Server 数据、客户端行为、当前模板或 `aion-server` 交叉证明后，才能进入显式忽略清单。

### 6.3 effect type 归一化

先对 231 种原始拼写做语法归一化，再对归一后的 174 种效果类型做语义映射：

- 去除无意义的大小写和分隔符差异；
- 将已确认的别名映射到同一 canonical type；
- 保留原始值，差异报告必须能回溯；
- 异常值不能自动归到“最相似”的效果；
- 每个 canonical type 必须对应现有效果类、明确的无操作语义，或新增的最小效果实现。

禁止用通用反射把 effect type 自动拼接为类名。显式映射表更容易审计，也能在重命名时立即暴露缺口。

### 6.4 `reserved` 参数映射

`reserved1...N` 不是通用位置参数。同一个位置在不同 effect type 中可能代表完全不同的值。映射必须以 effect family 为单位实现，例如：

```text
SkillATK_Instant
  reserved2  → 百分比伤害值
  reserved14 → 附加控制类型

Heal_Instant
  reserved... → 固定值、比例值、目标范围等该 family 专属语义
```

每个 family 的编译器应完成：

- 参数类型和范围校验；
- 默认值与字段缺失的区分；
- 真端枚举到现有模型枚举的转换；
- 子效果或联动技能引用校验；
- 至少一个真实技能样本的旧/新模板对照测试。

例如技能 `16526` 的真端字段包含：

```text
effect1_type=SkillATK_Instant
effect1_reserved2=21
effect1_reserved14=Stumble
cancel_rate=25
```

当前模板则包含百分比伤害、子效果技能 `8218`、武器条件、目标范围和 motion 等嵌套结构，且 `cancel_rate=35`。这证明转换不是字段改名；必须解释 `Stumble` 如何关联子技能、嵌套结构来自哪些真端字段，以及 25/35 差异哪一方符合目标版本。

### 6.5 关联数据

编译完成后至少校验：

- 技能 ID 唯一；
- NPC 技能引用存在；
- 子技能、条件技能和延迟技能存在；
- charge set、skill group 和 cooldown/delay group 一致；
- motion ID 或 motion 名称可解析；
- 技能名称/描述文本引用可解析；
- 武器、职业、目标类型和施放条件枚举合法；
- effect 所需的物品、NPC 或其他模板引用存在。

文本或 motion 只影响表现时也不能静默丢失，应按“阻断运行”或“允许运行但阻断发布”分级报告。

## 7. 派生缓存

缓存用于缩短启动时间，不改变权威数据边界。

缓存元数据至少包含：

- 真端 `skills.xml` 的 SHA-256；
- 字段字典摘要；
- 编译器格式版本；
- 输出技能数；
- 生成时间仅用于诊断，不参与命中判断。

写入流程：

1. 编译到同目录临时文件；
2. 对临时文件执行完整 JAXB/XSD/引用校验；
3. `fsync` 后原子移动到正式缓存路径；
4. 若文件系统不支持原子移动则启动失败，不覆盖旧缓存。

缓存摘要不匹配、缓存损坏或编译器版本变化时必须重建。不得在编译失败后继续加载旧缓存，否则运行数据将不再对应当前真端输入。

## 8. Shadow Load 与差异报告

在正式切换前，启动仍使用旧 `SkillData`，同时在测试或离线命令中编译真端数据，生成结构化差异报告。

对 14,410 个共同技能逐字段比较：

- 基础属性：等级、类型、目标、范围、施法、冷却、消耗；
- 条件：武器、职业、姿态、目标状态；
- 动作与 motion；
- effect 数量、顺序、类型和参数；
- 子技能和其他引用；
- 服务器特有的人工修正。

每个差异必须归类：

| 状态 | 含义 |
|---|---|
| 真端修正 | 旧模板错误，采用真端值 |
| 版本差异 | 有版本证据，按 5.8 目标版本处理 |
| 服务端兼容 | 当前引擎确需保留，形成显式补丁规则 |
| 纯表示差异 | 两种结构运行语义等价 |
| 未解释 | 阻止发布 |

兼容补丁必须是按技能 ID 或明确规则维护的小型补丁集，并在报告中给出原因。禁止复制整份旧模板覆盖真端结果，否则权威源会失去意义。

真端独有 84 个、当前服务器独有 70 个技能也必须逐项分类。最终运行集默认以真端 14,494 个为准；确有服务端内部技能时，应作为独立的 server extension 数据加载，不能伪装成真端技能。

## 11. 测试策略

只建立能阻止真实回归的测试，不复制 14,494 份样板用例：

1. 解析器测试：字段字典、稀疏值、空值、重复 ID 和损坏输入。
2. 参数化 family 测试：每种 canonical effect 至少一个真实技能样本。
3. 全量离线编译测试：数量、未知字段、未知效果和全部外键。
4. 差异快照测试：固定报告摘要，防止转换规则无意漂移。
5. 运行行为测试：选取伤害、治疗、控制、光环、触发、子技能、充能和 NPC 技能代表样本。
6. 封包测试：施放结果、效果状态、冷却、技能列表和重登恢复。
7. 缓存测试：命中、失效、损坏、原子替换和编译失败不回退。

正式切换前再进行一次完整构建和真实服务启动验证；方案开发期间使用聚焦测试，不需要每个小步骤都启动服务器。

## 12. 失败处理与回滚

### 12.1 启动期失败

解析、编译、校验或 NPC 关联任一失败：

- 不修改 `DataManager` 已发布引用；
- 不覆盖最后一个有效缓存；
- 输出技能 ID、字段、effect type 和原始值；
- 启动失败，禁止自动加载旧模板继续运行。

fail-fast 是为了避免“服务看似启动成功，但部分技能行为来自错误数据”的高风险状态。

### 12.2 发布回滚

迁移提交应保持为一个可整体回退的数据切换单元。回滚时：

1. 回退技能与 NPC 技能的加载切换提交；
2. 恢复旧 `skill_templates.xml` 与旧 NPC 技能数据；
3. 删除派生缓存；
4. 重新启动并校验旧数据摘要和代表性技能。

不要只回退 `skills.xml` 或只回退 `npc-skills.xml`，否则会再次形成外键不一致。

## 13. 风险与控制

| 风险 | 影响 | 控制方式 |
|---|---|---|
| `reserved` 语义判断错误 | 技能数值或行为错误 | family 显式编译器、真实样本、三方数据交叉验证 |
| 旧模板含人工修复 | 切换后回归 | 差异报告、最小兼容补丁集 |
| 未知 effect 被忽略 | 技能看似可用但少效果 | 未知类型和参数一律阻断发布 |
| 技能与 NPC 数据不同步 | NPC 施放空技能或报错 | 联合外键校验、原子发布 |
| 缓存陈旧 | 运行数据不是当前真端数据 | 输入摘要和编译器版本共同控制命中 |
| 整体移植其他引擎 | 大量接口与行为回归 | 仅参考局部语义，不复制整套引擎 |
| 启动内存/时间上升 | 部署超时或 OOM | 流式解析、派生缓存、基准门槛 |

## 14. 交付拆分

建议按可审查的小提交推进，但在满足全部门槛前不把不完整 `skills.xml` 放入 `definitions`：

1. 基线统计与差异报告工具；
2. sparse table 解析器及测试；
3. 基础字段编译器及测试；
4. effect family 映射分组提交；
5. 关联完整性与 NPC 联合校验；
6. 缓存、原子发布和 reload 统一；
7. 全量差异关闭及最终数据切换。

前 1 至 6 步可以在不改变正式运行数据的情况下合入。第 7 步必须一次性满足本方案的全部发布验收门槛。

## 15. 最终判定

直接使用真端技能数据是可行的，成本集中在一次性的字段语义编译和完整性验证。复用现有技能引擎比整体重写或移植 `aion-server` 风险更低、改动面更小，也更容易证明每个行为来自真端数据。

在迁移完成后，运行时仍只面对现有 `SkillTemplate`；维护者只更新真端 `skills.xml`、编译规则和极少量有证据的兼容补丁，不再手工维护一份独立的全量 `skill_templates.xml`。
