> status: **已按授权运行**（用户 2026-09-23 明确授权实测）。未改生产代码、未引入依赖、未提交。
> 探针: `JsonlItemProbe.java` + `run-jsonl-probe.sh` + `gen_compact_jsonl.py`
> 产物: `results-batch.txt`、`results-coldstart.txt`、`results-verify.txt`、本文件
> 对照基线: `.agents/summary/startup-perf/xml-parser-probe/`（2026-09-19，解析器替换探针）
> 环境: Zulu JDK 26.0.2.1 (aarch64, 10 核)，无服务端进程参与

## 1. 结论

最终推荐形态：**双字典 JSONL + 流式扫描 + restrict 解析结果共享**。同一 11 分片数据集（128,632 条记录）：

| 场景 | JAXB/XML（现状） | JSONL | 比值 |
|---|---:|---:|---:|
| 单分片热态 | 90.3 ms | 33.1 ms | 2.73× |
| 串行热态 | 990.2 ms | 300.1 ms | 3.30× |
| 串行冷启动 | 1660.4 ms | 651.4 ms | 2.55× |
| 并行稳态 | 185.9 ms | 67.5 ms | 2.75× |
| **并行冷启动（≈生产首次启动）** | **1168.4 ms** | **819.8 ms** | **1.43×** |

| 其他指标 | JAXB/XML | JSONL | 差异 |
|---|---:|---:|---|
| 稳态分配量（并行） | 574.6 MB | **522.5 MB** | **−9%** |
| 冷启动类加载数 | 1583 | **799** | **−50%** |
| 冷启动 JIT 编译 | 1874–2565 ms | **1042–1141 ms** | **约 −50%** |
| 磁盘体积 | 91,365,309 B | 36,581,706 B | **40.0%** |

**方案本身全面胜出**（算法成本 3.30×、分配量更低、体积 −60%、框架开销减半），正确性经 11,925,674 字段比对验证。

**但折算到启动墙钟收益有限**：与生产最接近的口径是并行冷启动，**省 348.6 ms**，约合静态数据窗口（8.05s）的 4.3%、
总启动（12–14s）的 2.5–3%。原因是并行下 CPU 是瓶颈，而 CPU 里约三成是 JIT 编译（§6.1）——
**要显著改善启动，该打的是 JIT，而不是数据格式**（§7）。

配套代价：约 20 个文件的改动、6 类必须逐条复刻的 JAXB 容错语义（§3）、与既有"XML 为唯一运行时来源"约束的冲突（§10）。

## 2. 实验设计

复用 `xml-parser-probe` 的方法论（同文件、同目标类型、独立 JVM、warmup + iterations、墙钟/CPU/分配量四项），扩展 4 个场景：

| 场景 | 数据 | 被测路径 |
|---|---|---|
| `jaxb-item` | item 分片 XML 8.3MB | JAXB `unmarshal` → `ItemData`（与 2026-09-19 基线一致，交叉验证 92.1 vs 101.1ms） |
| `sax-scan-item` | 同上 | SAX 扫描，只累加属性数（XML 词法层下限） |
| `jsonl-parse` | 紧凑 JSONL 4.6MB | 只解出 (键索引, 值) 对（JSONL 解析层下限） |
| `jsonl-item` | 同上 | 解析 + JAXB 注解驱动反射绑定 → `ItemTemplate` 对象图 + 等价 `ItemData.afterUnmarshal` 索引 |
| `batch-jaxb` / `batch-jsonl` | 全量 11 分片 | 串行处理全部，模拟生产 item 加载阶段的工作量 |
| `verify` | 全量 11 分片 | 逐字段比对两条路径产出的对象 |

**紧凑 JSONL 格式**：首行键表，之后每行只写非空字段的 `键索引:值` 对（JSON 数组形式）。

## 3. 正确性验证（先于性能）

**11,925,674 个字段逐一比对，3 处不一致**——且 3 处均为**数据中存在重复 id**（`110901029`、`169800175`、`169800476` 各出现 2 次）导致的一对多比较假阳性，与绑定器无关。

绑定器在实现过程中踩到 6 类 JAXB 边界，**每一条都是静默错误或崩溃**，是本次实验最有价值的副产品：

| # | JAXB 边界 | 不复刻的后果 |
|---|---|---|
| 1 | `List<T>` 字段 `getType()` 返回 `List` 而非 `T`，元素类型须取泛型实参 | `TradeinItem.id/price` 全部丢失（静默） |
| 2 | `@XmlAttribute` 上的集合字段（`Stigma.skill`，无 `@XmlList`）整个值作单元素 | 抛 `IllegalArgumentException`，加载中断 |
| 3 | 未知枚举值容忍：数据含 `armor_type="ARROW"`，模型无此常量 | JAXB 留 null 不报错；自写绑定器抛异常中断 |
| 4 | **无属性元素的存在性**：`<read/>`、`<disassemble/>`（全量 8,135 个）在"路径→值"编码里不产生任何对 | actions 列表少项（静默） |
| 5 | **数据比模型新**：`@activate_target`（31,883 次）、`instancetimeclear@sync_ids`、`@minion_list` 在模型里无字段 | JAXB 建元素、忽略该属性；错误实现会**连元素一起丢** |
| 6 | **列表元素序号必须进路径**：部分 `<add>` 无 `bonus` 属性，任何"属性名回绕"式推断都会错并元素 | `modifiers` 列表元素错位（实测 84,825 处不一致） |

第 4、6 条是**格式设计**层面的硬约束，不是实现细节：紧凑编码若不携带列表序号与空元素标记，就无法还原 JAXB 的对象图。
两条修正各使体积增加约 1 个百分点（58.1% → 59.2%）。

## 4. 性能归因（单分片）

| 层 | 墙钟 | 分配量 |
|---|---:|---:|
| XML 词法解析（SAX 纯扫描） | 41.1 ms | 0.4 MB |
| JAXB 绑定（92.1 − 41.1） | 51.0 ms | 45.9 MB |
| JSONL 词法解析 | 17.3 ms | 36.6 MB |
| 反射绑定（45.7 − 17.3） | 28.4 ms | 33.5 MB |

两点值得注意：

1. **XML 词法层只占 JAXB 总耗时的 45%**，其余 55% 是 JAXB 绑定本身。而反射绑定（28.4ms）比 JAXB 绑定（51.0ms）便宜近一半——
   这说明收益来自**两层同时变快**，不只是"JSON 比 XML 好解析"。
2. **JSONL 的分配量反而更高**（每行 `readLine` + 手工扫描都会造字符串）。JAXB 的 46.3MB vs JSONL 的 70.1MB，
   全量放大到 575.6MB vs 993.4MB。

## 4.1 分配量优化（+72.6% → +17.1%）

单字典方案的分配量倒退来自两处，都不在绑定层：

| 优化 | 做法 | 效果 |
|---|---|---|
| **值字典**（格式层） | 首行同时携带路径字典与值字典，行内只有整数索引。值不再逐条 `new String`，全体记录共享字典实例——`"true"` 出现 27,466 次、`"1"` 21,315 次，共享收益巨大 | 解析层分配 **37.0 → 12.3 MB**（−67%）；解析 **17.4 → 8.0 ms**；体积 **59.2% → 40.0%** |
| **流式扫描**（实现层） | 不把整个文件读成 `char[]`（双字典分片 3.3MB → 6.6MB char[]，正是与 JAXB 的分配量之差），改为固定 256K 缓冲跨块扫描 | 单分片 **55.0 → 47.0 MB**；全量 **764.1 → 673.8 MB**；代价是慢 3.5%（358.5 → 371.1 ms） |

**残余 +17.1% 的归属**：主要来自 `ItemTemplate.afterUnmarshal` 的 `restrict.split(",")`——全量 128,632 × 17 ≈ **218 万个 String**，
这是**两条路径的共同成本**（JAXB 同样支付）。若整体替换加载器，可让解析器直接从字符缓冲产出 `int[]` 交给 `restrict`，
跳过全部中间 String，预计再省约 100 MB，**完全追平甚至低于 JAXB**。该项需要改动 `ItemTemplate.afterUnmarshal`（生产代码），本轮未做。

**推荐形态：双字典 + 流式**。它比 readFully 版慢 3.5%，但分配量低 12%——启动期分配量直接喂给 GC（3.0 核·秒），比 3.5% 的解析时间更值得省。

## 4.2 restrict 解析结果共享（分配量反转）

`afterUnmarshal` 里的 `restrict.split(",")` 是全量最大的单项分配：128,632 条记录 × 17 ≈ **218 万个 String**，
外加同数量的 `String[]` 与逐记录 `int[17]`。而**全量只有 767 种不同的 restrict 取值**（每种固定 17 项）。

绑定器改为自行完成 `afterUnmarshal` 的收尾语义（`itemId` / `restrictsMax` / `weaponStats` 默认值三项与 JAXB 逐字对齐，
已验证），但 `restrict` 走**按值缓存**：解析只发生 767 次，且所有记录**共享同一个 `int[]` 实例**。

前置校验：`getRestrict()` 在当前代码库**零调用者**，`restricts` / `restrictsMax` 在 `ItemTemplate` 内只读。

**效果（全量 11 分片，热态中位数）：**

| 指标 | JAXB/XML | 双字典流式 + restrict 缓存 | 改善 |
|---|---:|---:|---:|
| 墙钟 | 990.2 ms | **300.1 ms** | **3.30×** |
| CPU | 985.7 ms | 298.1 ms | −69.8% |
| **分配量** | **575.6 MB** | **522.5 MB** | **−9.2%（反超）** |
| 单分片分配量 | 46.3 MB | 36.2 MB | −21.8% |

**至此三个维度全部优于 JAXB**：更快（3.30×）、分配量更低（−9.2%）、体积更小（40.0%）。

**尚未实现的部分**（字节级路线的剩余项）：当前解析仍经过 `char[]` 与字典 String，普通 int 字段走 `Integer.parseInt(dict[i])`。
改为纯 `byte[]` + token slice 直接解析可省掉 UTF-8 解码层（项目 2026-09-19 已实测该层不是瓶颈）与数字的字符串中转，
预估再省 <10%；`restrict` 这个最大单项已按字节扫描思想实现（见上）。

## 5. 全量冷启动对照（独立 JVM，首轮）

每个 arm 独立 JVM，各 3 轮，只取第 1 轮。**JAXB arm 含 `JAXBContext` 构建**——生产 `XmlDataLoader.unmarshalShard`
在首次 `sharedJaxbContext` 调用时构建它，属于静态数据阶段的一部分；JSONL arm 的绑定器元数据构建本来就在测量内。

| run | JAXB/XML | 双字典流式 | |
|---|---:|---:|---|
| #1 | 1879.2 ms | 631.2 ms | |
| #2 | 1660.4 ms | 711.9 ms | |
| #3 | 1657.6 ms | 651.4 ms | |
| **中位数** | **1660.4 ms** | **651.4 ms** | **2.55×** |

同 JVM 第 2/3 轮（稳态）：JAXB ≈1080 ms，JSONL ≈335 ms，热态比值 **3.22×**。

**首轮记账 / per-round accounting：**

| 指标 | JAXB | 双字典流式 | 差异 |
|---|---:|---:|---|
| 类加载数 | 1583–1585 | 799 | **−50%** |
| JIT 编译时间 | 1874–2565 ms | 1042–1141 ms | **约 −50%** |
| 分配量 | 596.7 MB | 531.2 MB | −11% |

**关键更正**：本报告早先版本担心"新解析器/绑定器代码会把 JIT 成本加码"（JIT 是静态数据阶段头号 CPU 单项 16.2 核·秒）。
实测相反——JAXB 要加载 1583 个类、烧 1.9–2.6 秒 JIT（**大部分是 JAXB 框架自身**：`jakarta.xml.bind` 实现、
注解元数据处理器、类族的反射支撑），而绑定器只需 799 个类、1.0–1.1 秒。**新增的十来个类远低于它替掉的框架开销。**

冷态比值 2.55× 低于热态 3.22×，但差距不再来自"新代码更贵"，而是冷态下共同的文件 IO 与对象构造占比更高。

## 6. 并行时序对照（≈生产 `loadItemData`）

固定池 `POOL_SIZE = CPU + 5 = 15`（对应 `XmlDataLoader.STATIC_DATA_POOL`），11 分片并发提交。
并行下线程级 CPU 失效，改用**进程级 CPU**（含 JIT/GC 线程）；分配量由工作线程自计后汇总。

**稳态（warmup=2, iterations=5）：**

| arm | 墙钟中位数 | 进程 CPU | 分配量 |
|---|---:|---:|---:|
| `parallel-jaxb` | 185.9 ms | 1324.2 ms | 574.6 MB |
| `parallel-jsonl` | **67.5 ms** | **478.5 ms** | 522.5 MB |
| 比值 | **2.75×** | **2.77×** | −9% |

**冷启动首轮（独立 JVM）：**

| run | JAXB | 双字典流式 |
|---|---:|---:|
| #1 | 1515.0 ms | 741.0 ms |
| #2 | 1168.4 ms | 819.8 ms |
| #3 | 1167.3 ms | 853.1 ms |
| **中位数** | **1168.4 ms** | **819.8 ms** |
| 进程 CPU 中位数 | 7211.7 ms | 5230.8 ms |

**冷启动并行仅 1.43×**，远低于串行冷启动的 2.55× 与并行稳态的 2.75×。

### 6.1 为什么并行冷启动收益收窄

两个 arm 的平均核利用率都是 **6.0 核**（进程 CPU ÷ 墙钟，10 核机器）→ **CPU 是瓶颈**，于是
**墙钟 ≈ 进程 CPU ÷ 并行度**，墙钟收益 ≈ CPU 收益。CPU 从 7211.7 → 5230.8 ms，即 **−27%**。

JIT 编译是这里的隐藏大头：JAXB 首轮烧 1.9–2.6 s JIT，JSONL 烧 1.0–1.1 s，而 JIT 跑在独立编译器线程上、
与 11 个工作线程抢同样的核。**并行把"JIT 抢占"的成本直接摆到关键路径上**，两个 arm 一起被拖慢，差距收窄。

## 7. 折算到启动墙钟

- item 加载阶段现状约 **1–1.5s**（2026-08-22 分片化成果：6s → 1–1.5s），11 分片并行。
- **与生产最接近的口径是"并行冷启动"：1168.4 → 819.8 ms，省 348.6 ms。**
- 相对静态数据窗口 **8.05s** 约 **4.3%**；相对总启动 **12–14s** 约 **2.5–3%**。
- 串行口径（冷 2.55× / 热 3.30×）只用于判断方案本身的算法成本，**不可用于外推启动收益**——
  并行下墙钟由 CPU 总量决定，而 CPU 里约三成是 JIT 编译。
- 注意本轮并行只跑 item；生产同时跑 NPC 分片与 12 个定义，抢核更凶。那会**同时**拖慢两个 arm，
  比值大体保持，绝对省额可能进一步摊薄。

## 10. 与既有约束的关系

`2026-09-19-static-data-critical-path-attribution.zh-CN.md` 第 0 节记录了用户约束：

> **XML 加载不使用二进制缓存**：既要支持临时修改 XML 后 reload 立即生效，也不接受"改一次 XML 就要重新生成二进制"。
> 因此候选 1（构建期紧凑/二进制缓存）**否决**，后续不得再作为推荐项。

紧凑 JSONL 若作为**运行时唯一来源**，与该约束的冲突点是「改一次就要重新生成」——
从 XML 生成 JSONL 是一次确定性转换（`gen_compact_jsonl.py`，11 分片 3 秒），但**仍需在改数据后手工/脚本重跑**，
不如直接改 XML 即时生效。若保留 XML 为源、JSONL 为派生物，则仓库体积不下降（两套并存）。
