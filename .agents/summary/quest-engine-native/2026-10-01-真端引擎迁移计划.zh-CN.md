## 0. 口径与本次修正

### 0.1 用户已锁定的口径

1. **放弃当前零售任务引擎**（表 → per-family 编译器 → 自造 IR → 通用 dispatcher）；零售任务改为**完全按真端的表驱动引擎**。
2. **XML-only 任务继续走现有 IR 引擎**；真端表覆盖任务按族切到 native 后不得再回退 XML/IR。XML 车道内部不改，后续退役单独立案。
3. 真端**没有手写硬编码**，但有离线 codegen 产物（每任务一行的相机注册）。我们的等价物是**启动期由真端表构建注册表**，绝不手写任务常量。
4. `src/main/resources/quest` 等**客户端派生资源最终退场**，运行时不再读客户端派生 TSV。
5. **台账不保留降级**：本服自造台账（retention list、string-id map、npc alias、legacy heal rows、TSV manifest）只作为过渡期迁移门禁的临时输入；**终态全部删除**。不得把“降级为构建/测试资源”写成终态处置。
6. **以真端实际运行任务的方式驱动，非旧基础兼容**：严禁在旧 IR 状态机、旧 Catalog、旧 Handler 或兼容 Overlay 上修修补补；必须直接以真端表驱动 Native Handler、ProgressCamera、HtmlPages 驱动对话，整族原子切换，同批删除旧编译器。遇阻排查真端原码与表，与真端事实保持一致。
7. **彻底废除“部分切换、冻结行留在旧路径”的妥协**：排查真端证实，所谓 22 个歧义与 150 个缺名全为假象（真端原名唯一，缺名实为 `quest_ai_name` 与副本区域杀怪）。SimpleHunt 家族具备 100% 全量原生切换条件，不搞新旧双轨并存。

### 0.2 本次修正（对上一版的否决记录）

- 上一版把 `retail/` 下本服台账写成“迁移完成后降级为构建/测试资源”。
- **用户否决**：台账不应保留降级。
- 本文档改为：**过渡期临时使用，终态删除；测试若要证据，必须从真端表重算/重生成，或使用带客户端出处的一次性证据快照，不得长期保留为 `src/test` 台账。**

### 0.3 非目标

- 不改 XML-only 车道的编译/调度内部实现（只经受控共享接口接入）；不为未切换 retail 家族扩展旧 retail→IR 能力。
- 不改客户端；不新增客户端协议。
- 不发明任务 id、页 id、坐标、计数、NPC 映射。
- 不启动/停止服务器；不在未授权时跑 Maven/构建。
- 不用旧 XML/handler 去“对齐”真端语义。证据优先级：**真端表/原码 + Aion 5.8 客户端 > 旧 XML/handler**。

### 0.4 防漂移硬约束（本计划的验收前提）

本计划中的“漂移”定义为：**任何让派生台账、客户端 TSV、旧 XML/IR 形状重新成为运行时权威，或用兜底/静默回退掩盖未决项的变化。**

1. 运行时权威只有真端表 + 服务端静态数据；客户端数据/台账最多是过渡门禁或测试证据。
2. 未决项必须 `EVIDENCE_REQUIRED`/fail-closed；禁止 default、fallback、“保留现状”式兜底。
3. 门禁锚定真端表行/客户端页动作，不锚定 IR 指纹/当前形状；指纹只作回归证据。

漂移根因、反漂移门、预警信号与每批检查表见 §8 + 附录 D；以当前章节条数为准，不沿用旧计数。

### 0.5 代码精简、按族切换与 XML 车道保留口径

1. **零售车道按真端方式驱动，完全一致**：真端表 → 启动期注册表/处理器对象；retail 任务不再翻译成 IR，不经过 XML catalog。
2. **按族即时切换，不保留 shadow 兼容层**：一个家族完成真端语义、族级门禁与代表性验收后，该族真端表覆盖任务同批切换到 native 车道，并删除该族旧 retail→IR 编译器、overlay、客户端派生读取和双路径入口。
3. **整族切换前置约束**：家族内只要有表行语义、身份证据、raw vars 存档兼容或失败模式未闭环，整族继续停留在当前实现；不得让部分行 native、部分行回退旧 retail→IR。
4. **XML 车道只服务 XML-only 任务**：真端无表覆盖或证据未坐实的 XML 长尾继续走现有 IR；该车道内部不改、不新增功能、不为 retail 兼容扩展。
5. **后续退役单独立案**：XML 长尾退役不是本次阻塞项；本计划只保证 retail 表车道与 XML-only 车道边界干净、可独立退役。
6. 代码精简的判定不是行数，而是：删除后 retail 语义仍完全由真端表驱动，XML-only 任务仍能运行，且没有任何兼容路径重新成为第二事实来源。

### 2.3 注册机制（真端 codegen 产物）

- 真端：每任务一段生成式 C++ 函数；启动期写索引表 `*(ctx + 0xa8 + idx * 8) = fn`（`MainServer_ScriptDLL64/fun/fun_731.cpp:6214`），调用点在 `MainServer_ScriptDLL64/fun/fun_229.cpp:1093`。
- 我们的等价物：**启动期由同一张真端表构建 `CameraRegistry`**；参数逐行可与表对拍，行为等价，不逐字复制 C++。
- 明说边界：真端是“离线生成每任务脚本”，我们是“启动期由表构建注册表”；这是允许的等价替代，但必须做到：参数逐行可对拍、缺行 fail-closed、重复/矛盾 fail-fast。

### 2.7 真端 NPC 命名与怪物匹配事实（消解 22 假歧义与 150 假缺名）

1. **SimpleHunt 22 个所谓的“名字歧义”实为模拟器数据字段错位**：
   - **真端事实**：真端 `Map/XML/npcs.xml` 中，每个 NPC 的 `<name>` 均唯一（如 `278516` 为 `Theon`，而 `800274` 为 `event_hc_Theon`）。

### 2.8 真端 DataDriven 击杀变量布局与真实数据事实（消解 7 个假宽计数）

1. **变量布局与掩码**：逆向分析 `MainServer_ScriptDLL64/fun/fun_731.cpp` 中 DD 击杀分发函数 `FUN_180c46020`，DD Hunt 变量布局标准为 `step` 占 bits 0..5（低 6 位），后接 4 个 6 位子计数器（shift 6, 12, 18, 24，掩码 `0x3f`，最大 63）。
2. **原文逐行核查**：查验真端 `Map/XML/data_driven_quest.xml` 原文：
   - 任务 10034、20506、25082 的实际击杀需求均为 `1`；
   - 任务 20503、20507、25050、25051 根本无 Hunt 步骤；
   - 之前旧分析脚本统计出的 `90` 实为刷怪点朝向角（heading=90°），`120` 和 `300` 是怪物消失倒计时（despawn_time）！
   - 全表仅 `80817` 一个活动任务包含 100 杀；它**不走 10 位相机**——DD 只有「6 位步号 + 4×6 位组槽」一种布局，target=100 > 63 会在第 64 杀处槽回绕（并污染下一组槽），`(slot < target)` 永不稳定 ⇒ **该任务在真端自身无法通过击杀完成**。其余 DD 击杀全部在合法 6 位计数（最大 1 杀）范围内 ⇒ 「宽计数」阻塞解除（详见 §10.3-#5 裁定与 `p0a/semantic-matrix-dd-wide-count.md`）。

### 2.9 真端任务驱动与事件派发原生机制

1. **原生任务处理器实例**：
   - 真端对任务家族使用原生 C++ 类处理：`SimpleHuntQuest`、`SimpleSerialHuntQuest`、`SimpleCollectQuest`、`SimpleItemPlayQuest`、`SimpleUseItemQuest` 及 `QuestProgressExtraInfo_*`。
   - 表解析后直接生成处理器实例与相机绑定，不存在“表 → IR 编译器 → 虚拟状态节点 → 旧 Dispatcher”的中间层。
2. **生命周期与相机推进**：
   - 玩家事件（击杀/对话/用物）到达时，直接由原生路由分发至对应任务实例；
   - 状态只维护 `status` + 32 位 `raw vars`；
   - 相机三守卫（`status == START`、`vars < 0x40000000`、槽位未满）检查通过后，单次事件直接位运算加一（`vars += 1 << shift`），超杀静默；
   - 满值走推进写入（`+0x100`），未满走普通写入（`+0xf0`），统一经 `StatePort` 持久化并下发 `SM_QUEST_ACTION` 同步客户端。

## 6. 引擎设计（Java 侧）

### 6.1 包名与边界

- `native` 是 Java 关键字，不能作为包名。统一采用 `com.aionemu.gameserver.questEngine.tablelane`；文档中的“native 车道”指该真端表驱动车道，不使用 JNI/本机代码。
- 家族切换前，旧 retail→IR 编译器只允许按原样继续服务该家族；不得为它新增兼容逻辑。
- 家族切换批必须同时交付新 handler、生产路由接入和该族旧路径删除，三者缺一不可。
- XML-only 车道继续使用现有 IR；不为 retail 任务扩展任何 XML 车道能力。

### 6.2 组件与职责

| 组件（暂名） | 职责 | 关键约束 |
|---|---|---|
| `NativeQuestTableLoader` | 解析真端家族表、DD、quest.xml、HtmlPages.xml | UTF-16/DTD 感知；只读、不可变行模型；解析失败 fail-fast；记录来源 hash/转换脚本 |
| `RawQuestVarsCodec` | 32 位 raw vars 的 6 位/10 位读写 | 不复用 `QuestVars`；宽度由表行相机型别决定；非法位形 fail-closed |
| `ProgressCamera` | 表驱动相机推进 | 一次事件只加一；超杀无动作；按 P0a 矩阵区分 `0xf0`/`0x100` 副作用 |
| `CameraStepSpec` / `CameraRegistry` | 表行 → 相机步骤，启动期构建 | 不可变；同任务不混宽度；缺行/矛盾 fail-fast；逐行对拍 |
| `NativeQuestOwnerResolver` | 真端表 id 集合与 XML-only id 集合求交/求路由 | 交集失败；身份证据未证则整族不切换；替代 retention 台账 |
| `NativeQuestStatePort` | 统一写 status/raw vars、持久化标记、事务提交与客户端同步 | 不绕过持久化/同步边界；通道副作用按 P0a 矩阵；失败回滚语义可测 |
| `HtmlPagesRegistry` | `HtmlPages.xml` id↔页名 | 唯一页来源；未知页 fail-fast |
| `NativeNpcNameResolver` | 服务端静态数据中的 npc/monster/item/zone 名 → id | 只允唯一解析；歧义/缺失 `NATIVE_NAME_UNRESOLVED`；不读 alias 台账 |
| `NativeAcquireRouter` | 接取事件 → START | 覆盖表声明的 Talk/ItemPlay/LevelUp/EnterWorld/LevelUpLogIn/EnterArea；未知 kind fail-closed |
| `NativeProgressHandlerFactory` | DD progress 类别 → handler | 8 类；未知类别 fail-closed；`>63` 未证行冻结 |
| 家族 handler | SimpleHunt / SimpleSerialHunt / SimpleTalk / SimpleCollectItem / SimpleUseItem / SimpleItemPlay / CombineTask / DataDriven | 参数全部来自表行；不生成 IR；同族切换后旧编译器删除 |
| `NativeReportRewardFlow` | 报告、`can_report`、奖励窗、多交付 NPC、职业奖励 | 奖励窗页与选择按钮同 owner；缺声明 fail-closed |
| `NativeQuestRuntimeRouter` | 生产唯一入口：native 或 XML-only IR | 无回退；native 失败显式错误；`questId=0` 广播不得双触发 |

### 6.3 启动期校验（fail-fast 清单）

错误码可按代码风格命名，但语义必须显式且可测试：

| 错误码（建议） | 触发条件 |
|---|---|
| `NATIVE_TABLE_PARSE_FAILED` | 表缺失、格式/编码错误、来源 hash 不符 |
| `NATIVE_TABLE_ROW_MISSING` | 家族表任务缺关键行/字段 |
| `NATIVE_OWNER_CONFLICT` | quest id 同时出现在真端表与 XML-only 目录 |
| `NATIVE_OWNER_IDENTITY_UNPROVEN` | 表 id 存在但身份三源或可达性证据未闭环 |
| `NATIVE_CAMERA_WIDTH_MIXED` | 同一任务解析出 6 位与 10 位相机 |
| `NATIVE_CAMERA_REQUIRED_EXCEEDS_MASK` | required 超过对应宽度 mask |
| `NATIVE_CAMERA_FULL_VALUE_INVALID` | fullValue 不是各槽满值合法组合 |
| `NATIVE_RAW_VARS_INVALID` | 现有存档 raw vars 位形未通过家族迁移判据 |
| `NATIVE_PAGE_UNREGISTERED` | 行引用页 id 不在 HtmlPages |
| `NATIVE_NAME_UNRESOLVED` | npc/monster/item/zone 名缺失、歧义或映射不唯一 |
| `NATIVE_CATEGORY_UNKNOWN` | DD progress/acquire 类别未知 |
| `NATIVE_COUNTER_WIDTH_UNRESOLVED` | `>63` DD 行计数宽度未由 P0a 还原 |
| `NATIVE_CAN_REPORT_UNMODELLED` | 使用 `can_report` 的行未进入 native flow |
| `NATIVE_REWARD_WINDOW_OWNER_MISMATCH` | 奖励窗页与选择按钮不在同一对话 owner |

### 6.4 运行时数据流

```text
玩家事件（击杀/对话/进区/用物/升级/登录）
        │
        ▼
NativeQuestRuntimeRouter
   ├─ owner=native ─► 家族 handler / DD progress handler
   │                      ├─ ProgressCamera（6/10 位）
   │                      │      ├─ 0xf0 普通写入
   │                      │      └─ 0x100 推进写入
   │                      └─ NativeQuestStatePort
   │                             ├─ status/raw vars 持久化
   │                             ├─ 事务提交/回滚
   │                             └─ 客户端同步
   └─ owner=xml-only ─► 现有 IR 引擎（内部不改）
```

禁止：native 失败后改走 XML/IR；同 quest 双路径；绕过 state port 直接改 DB 或发同步包；把客户端 TSV 当运行时输入。

### 6.5 与 XML 车道共存和按族切换

- 共享层仅限：玩家串行执行协调、任务状态存储（status + raw vars）、事件总线、客户端契约门；共享接口不得暴露 IR 编译器/节点图。
- XML-only 任务继续走现有 IR；native 任务只走真端表 handler；两车道的任务 id 不得重叠。
- 过渡期的 central router 是唯一生产入口：已切换族直接进 table handler；未切换族可进入无 overlay、无 fallback 的旧族分支；该旧分支随各自家族切换删除，最终 P8 删除整个 shell。
- 任何已切换族不得再引用 `RetailQuestDriver.overlay`、`overlayProduction`、family compiler、`RetailClient*` reader 或 IR catalog；违反即双事实来源。
- 家族切换矩阵必须记录：family、行数、`NATIVE_READY` 行集、身份/raw vars 未证行集、生产接入点、旧编译器/TSV reader 删除清单、focused test、客户端验收状态。
- 家族内存在未闭环行时整族不切换；不得将该族拆成“部分 native + 部分旧 retail→IR”。该族可继续按切换前原实现运行，但不得新增兼容分支。
- 每族至少一个代表任务完成 Aion 5.8 客户端验收后才可标记完成；未跑只能 `PENDING_CLIENT`，最终收口不得把 `PENDING_CLIENT` 家族计为已验收。

## 8. 不变式与门禁（全程不得破）

1. **单 owner fail-fast**：一个 quest id 只能属于一个运行时；表 id 与 XML-only id 交集启动失败。
2. **按族整批切换**：家族证据未闭环时整族停留旧实现；不得部分 native、部分旧 retail→IR。
3. **同批删旧**：家族切换提交必须同时删除该族 retail→IR 编译器、overlay、客户端派生读取和双路径入口。
4. **XML-only 冻结**：XML IR 只服务 XML-only 长尾；不得为 retail 兼容新增能力；后续退役单独立案。
5. **不许发明**：id、页、坐标、计数、NPC 映射缺声明即 fail-closed。
6. **身份轴**：owner 判据必须包含真端声明、客户端正文、可达性三源；只有表 id 或路由自洽不足。
7. **raw vars 安全**：native 写入前必须有存档位形结论；异常位形不得静默规范化。
8. **相机单一实现**：6/10 位 codec、双通道副作用、state port 在 native 车道各只有一份；禁止第二布局。
9. **族级逐行对拍**：每族表行事件序列输出 `ADDED 0 / REMOVED 0`；禁止单 ID 补丁。
10. **客户端数据不进运行时**：客户端证据只作测试/验收，且必须记录版本、路径、hash 与抽取命令。
11. **台账不降级**：五个台账只作过渡审计，终态三层删除门清零，不迁入 test/build。
12. **零任务硬编码**：quest 专属事实不得进代码；白名单必须附证据、测试、责任人与过期条件。
13. **奖励窗 owner**：页与选择按钮同 owner；不得追加在 terminal `CLOSE` 后；退场判据只认页下发。
14. **失败显式**：所有未知/冲突/证据不足均错误码 fail-closed；XML-only 之外无 IR 回退。
15. **基线纪律**：QE-112 未落地或未裁决前不得冻结 P0a 验收数字；差异先归因。
16. **提交纪律**：不用 `git add -A`；只 stage 本批路径；不 push；不启停服务器；构建先授权。
17. **工作区纪律**：不建 worktree；若确需临时 worktree，外部路径、仅验证、立即 remove+prune。

> 每批开工/收口逐项勾选附录 D.4；出现 D.3 任一预警即停批归因，不得先改后补证。

## 8.5 阻塞排查与真端对齐（阻塞就排查真端，和真端一致）

依据用户明确指令：“**以真端实际运行任务的方式驱动当前模拟器的任务驱动，不是在旧的基础上兼容，阻塞就排查真端，和真端一致就行**”，针对前期梳理出的所有阻塞点，深入真端原码（`<真端根>/server58-source/`）与数据（`<真端根>/Map/XML/`）进行逐项求证，排查结论与真端对齐解法如下：

### 1. 阻塞点一：SimpleHunt 22 个所谓的“名字解析歧义 (AMBIGUOUS)”
- **真端事实**：真端 `npcs.xml` 中，每个 NPC 的英文开发名 `<name>` 均唯一（如 `278516` 为 `Theon`，而 `800274` 为 `event_hc_Theon`）。
- **模拟器根因**：模拟器 `npc_template_*.xml` 将韩文/本地化名称填入了 `name`（如 `name="theon"`），而真端的唯一 `<name>` 完整保留于 `name_desc` 字段。原 `NativeNpcNameResolver` 将 `name` 与 `name_desc` 无优先级平级合并索引，导致本地化同名引发假多义。
- **真端对齐解法**：调整 `NativeNpcNameResolver`，以 `name_desc` 作为第一权威索引。22 个所谓歧义 NPC 立即 100% 精确唯一解析，歧义归零。

### 2. 阻塞点二：SimpleHunt 150 个所谓的“怪物名缺失 (MISSING)”
- **真端事实**：真端 `Quest_SimpleHunt.xml` 里的怪物名字，包含两类真端原生机制：
  1. `<quest_ai_name>` 怪物组别名：如 `Ab1_1131_Boss_Da_Q1737` 匹配真端 `npcs.xml` 的 `<quest_ai_name>`，对应 NPC `263006` 等深渊首领守护者；
  2. `WorldId.xml` 副本区域全图击杀：如 `IDAbRe_Low_Divine` 对应真端 World ID `300060000`，表示整张副本地图怪物的全杀任务。
- **真端对齐解法**：`NativeNpcNameResolver` 补充加载 `quest_ai_name` 别名映射，并识别副本世界全图击杀规则，150 个怪物名完全闭环。

### 3. 阻塞点三：DataDriven 8 个所谓的 `>63` 宽计数任务
- **真端事实**：逆向分析 `ScriptDLL64.c` 中 DD 击杀分发函数 `FUN_180c46020`，DD 变量布局为 `step`（bits 0..5）+ 4 个 6 位计数器（shifts 6, 12, 18, 24，掩码 `0x3f`）。查验 `data_driven_quest.xml` 原文发现，8 个任务中有 7 个（10034、20506、25082 等）是旧分析脚本将刷怪点朝向角（heading=90°）和怪物消失倒计时（120/300秒）误判为击杀数，实际击杀需求均为 `1`，完全属于合法 6 位计数；仅 80817 一个活动任务含 100 杀，深挖 6 位组槽算术后坐实为「第 64 杀槽回绕并污染下一组、`(slot < target)` 永不成立 ⇒ 真端自身不可完成」（**不是** 10 位相机）。
- **真端对齐解法**：DD 击杀计数全部在标准 6 位组槽布局内，原宽计数阻碍消解；80817 按真端原样算术复刻（含溢出行为），见 §10.3-#5 裁定。

### 4. 阻塞点四：模拟器任务驱动方式（摒弃旧兼容，走原生驱动）
- **真端事实**：真端不存在“任务表 → IR 编译器 → 虚拟状态节点 → 通用旧 Dispatcher”的中间层。真端是直接由表加载生成原生任务类对象（如 `SimpleHuntQuest`），通过不可变相机注册表推进 32 位 raw vars，由统一状态接口持久化并同步客户端包 `SM_QUEST_ACTION`。

  1. 建立纯粹的原生表驱动车道（`com.aionemu.gameserver.questEngine.tablelane`）；
  2. 在事件入口建立原生分流（`owner == NATIVE_TABLE` 直接派发给原生处理器，不进入旧 IR 流程）；
  3. SimpleHunt 家族实现 100% 全量原生驱动，同批次彻底删除 `RetailSimpleHuntDefinitionCompiler.java` 专有逻辑，切断旧 IR 编译，零影子兼容层！
