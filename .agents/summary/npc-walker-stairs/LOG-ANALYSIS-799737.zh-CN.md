## 0. 结论

1. 对象 23942 = **799737**（编队偏移 `(0,-8)`）：窗口内四个目标点与
   `glp(prev, cur, OFFX[4], OFFY[4])` 逐点吻合（偏差 ≤0.0001m），依次为 step→3/4/5/6 的编队航点。
2. 服务端 218 个 tick **全部贴地**（`newZ − 地面 ≡ 0.0000`），每 tick 实测位移 0.09–0.25m
   （移动周期 100ms/200ms 两档，行走速度 ≈1.0 m/s）——服务端侧无问题。
3. 残留跳帧可用离线客户端模拟完全复现，机制 = **前视过长**：
   v2 前视 = max(1m, 速度×0.3s) = 1.0m，而客户端每 tick 只走 0.1–0.2m ⇒ 客户端一个 tick 只爬弦线
   行程的 1/5–1/10，台阶/坡沿处竖向滞后于地面（**入地**，实测最深 −0.118m），下一包把位置吸附回
   地面真值（**拉起来**，实测单次 +0.167/+0.141m）。且换腿后门控要等 6–7 个 tick（最长 3.1s）才
   激活流式，期间客户端走 8–9m 的长弦，首个流式包到达时一次性拉起。
4. 前视距离扫描（自适应 `L = max(0.15, K × 每 tick 实测位移)`，模拟客户端「吸附 from → 沿弦走一个
   tick」）：

| 前视 | 每 tick 竖向修正（pop）| >4cm 次数 | 客户端相对地面偏差 |
|---|---|---|---|
| L=1.0m（v2 现状）| p90≈2.8cm，max 11.3cm | 9 | −0.109 … +0.113 |
| 1.5×实测位移 | p90≈0.4cm，max 8.4cm | 4 | −0.055 … +0.084 |
| **1.3×实测位移（v3 采用）** | **p90≈0.2cm，max 8.9cm** | **3**（均在台阶棱线）| −0.067 … +0.089 |
| 1.15×实测位移 | p90≈0cm，max 3.5cm | 0 | −0.029 … +0.035 |

⇒ 前视 ≈ 一个下发周期的行程时弦线贴住地面，周期性入地/拉起基本消失；同时必须每个 tick（含换腿首
tick）补发，否则长弦阶段的拉扯仍在。1.3 相对 1.15 多出的 3 次 >4cm 都在最尖的棱线处，换来
+30% 的「客户端不先到点」余量（防 v1 停-跳复现），取 1.3、1.15 作为旋钮下限。

## 3. v3 修正（已实现，待实机复测）

`src/main/java/com/aionemu/gameserver/controllers/movement/NpcMoveController.java`：

1. **前视 = 本 tick 实测位移 × 1.3**（`walkStreamLookahead`）——自动适配 100/200/500ms
   三档移动周期；用实测位移而非计时推算，休息后恢复的首个 tick 不受暂停时长影响。
   （初版下限 0.15m 经实机否决，见 §3.1：已改为 1m 下限。）
2. **去掉地形门控**：行走态每个移动 tick 都补发（`shouldStreamWalkGround` 不再有粘滞参数），
   换腿首 tick 即发短段，**不再下整段长弦**（原 `!destinationChanged` 特例删除）。
3. 服务端逐 tick 贴地（AIM-009）保持成对不变。

聚焦测试：`NpcMoveControllerWalkStreamTest` 3/3、`NpcMoveControllerPathTest` 62/62（IDEA MCP，0 失败）。

## 3.1 v3 实机第二批：前视 0.33m 触发客户端「接近目标即判到达」（已按 1m 下限回修）

v3（前视 = 1.3×实测位移 ≈ 0.16–0.33m）实机：台阶入地/拉起消失（达标），但**多个巡逻**
（含 203112、11041、29077）出现「卡一下→原地走→往前走一小段→又原地走→才停下」的停-走-停。
排查：新抓 `log/aidebug.log`（23:06–23:07）显示**服务端侧完全平滑**（11041/29077 每 tick 稳定
前进 0.25m，流式段 0.33m = 设计值，无 <5cm 的停滞 tick）⇒ 现象在客户端渲染侧。

归因：客户端对 NPC 移动包**接近目标即判定到达**——前视低于该门槛时每个 tick 都被判到达，
走-停-走；实测门槛区间：**0.33m 触发、1m（v2 长期）不触发**。
修复：前视下限 0.15m → **1.0m**（`WALK_GROUND_STREAM_MIN_LOOKAHEAD`），即
`前视 = max(1m, 本 tick 实测位移 × 1.3)`；其余（每 tick 补发、换腿首 tick 即发短段、
逐 tick 贴地）不变。聚焦测试 3/3 + 62/62（2026-10-06 IDEA MCP），待实机复测。

## 3.2 拐角「顿一下 → 原地踏步 → 换方向走」（行走态朝向瞬跳，已加转身平滑）

前视下限回到 1m 后实机回报：**拐角处仍有顿挫**（「原地踏步然后继续换方向走」）。最新日志
（23:16 窗口，23422）复核：

- 拐角前后**无停包**：掩码全程 0xEA（不走 STARTMOVE/停止分支），到点后下一段在同毫秒内开始
  （`MC perform stop` + `MC: moveToNextPoint started` 同一时刻），移动在下一个 tick 恢复（间隔
  0.097–0.099s = 1 个移动周期）。
- 到点时客户端仍在上一段目标的行走途中（最后流式目标距航点 −0.11/−0.23m，未到点），所以顿挫
  不是「服务器停」造成的，而是**新段在一个包内把方向/朝向瞬跳了 ~37°**，触发客户端的原地转身
  （转身动画期踏步）。
- 处理（待实机复测）：**行走态朝向逐 tick 过渡**——`stepHeadingDegrees`（最短弧、单 tick ≤12°、
  归一化 (−180,180] 保持原 heading=度/3 编码），腿切换时不再瞬跳朝向；路径本身不变（不走位/寻路
  语义不动）。若实机证明客户端转身不依赖朝向字节（而是跟运动方向），则需做路径级圆角（更大改动）。

## 3.3 收尾段「提前停住 → 下一段回吸」：最后 1m 无包、最后目标距航点 0.24m（已改为收尾段直接以航点为终点）

数据：`log/aidebug.log` 2026-10-06 23:23:42–23:24:10，对象 21798 = **205294 Tenos**（Ermona 编队领队，
行走速度 ≈1.48 m/s，200ms 档、每 tick 行程 ≈0.29m）。同窗口的 `MC perform stop` ×5 +
`Can't change substate … from WALK_WAIT_GROUP` 是编队等待循环重复调用 `pauseAtRoutePoint`（只走
`resetMove` 日志、**不下发停包**），与画面无关，先排除。

判读（step 16 段，航点 = 1654.7345,1489.9434,119.375）：

- 段内流式包长恒 = 1.0m（前视下限生效），到点前最后一次流式包 `to` 距航点 **0.24m**：
  `23:24:09,641 walkGroundStream from=1654.8951,1491.1725 to=1654.7655,1490.1809`（剩余 1.2396m）。
- 其后 4 个 tick（09,835 / 10,028 / 10,223 / 10,415）服务端仍在推进（每 tick ≈0.29m、全部贴地、
  mask 全程 −22），但**一条流式包都没有**：旧实现的补发门控是「剩余距离 > 前视才补发」，
  剩余 1.2396m → 0.9485m 跨过 1.0m 阈值后就不再补发 ⇒ 段末最后 ~1m 客户端手里只有
  「距航点 0.24m 的旧目标」。
- 客户端按「起→终直线、到达即停」走完这个旧目标就停住（比服务端最终位置/航点还差 0.24m）；
  停顿（本窗口 4–13s）后下一段首个包起点 = 服务端当前位置 ⇒ 客户端被向前吸 0.24m 再起步。
  与实机「停止之前也会原地走几步」「转方向时先原地走几步」的观感一致（提前停 → 回吸 → 起步转身）。

修正（本次，待实机复测）：

1. `shouldStreamWalkGround(walkPathSubState, reachedWaypoint)` 去掉「剩余 > 前视」门控：行走态只要
   到点判定未成立（`reachedWaypoint`：XY ≤ MOVE_OFFSET 0.05m 且 |ΔZ| ≤ 0.25m）就每 tick 补发。
2. `walkGroundStreamTarget` 在剩余 ≤ 前视时**直接返回航点本身**（不再返回 null/前视点）：
   段末最后 ~3–4 个 tick 的包目标 = 航点，客户端恰在航点停下，下一段起步无回吸、无瞬移。

62/62（2026-10-06 IDEA MCP）。

## 3.4 203111（Spiros）「很轻微的抖动」：收尾段包目标落进客户端到达判定区间（已加收尾余量）

  同比例步长抵消）；

- 流式包 203/207 tick 有包（4 个到点 tick 无包，符合设计），包起点 = 该 tick 位置（错位 0 条），
  段长 1.0m（183 条）+ 收尾段递减；

到达（停一下、下个包再起步），且最后一次判到达的位置距航点最多差 ~0.3m，段落切换时被回吸。与
「很轻微的抖动 / 往前走不顺」一致；这也说明 §3.3 的「收尾段取航点本身」只解决了一半（去掉了
0.24m 提前停），收尾段的*包目标距离*本身还需要设下限。

**修正**：收尾余量 `WALK_GROUND_STREAM_FINAL_MARGIN = 0.75m`——距航点 ≤0.75m 后停发；此前

包目标不再落进到达判定区间。余量取值：> 实机触发点 0.33m、< 前视下限 1m（保证最后一个包的目标
就是航点本身）。

**下一个候选旋钮（本次未改）**：窗口内该 NPC 的移动 tick 间隔在 100/200ms 两档高频翻转
（110×100ms + 90×200ms，游程 1–5）——分档按「最近玩家距离 30m」判定，玩家贴着 30m 边界观察时
档位来回切；对照已验收顺滑的 799737 窗口是稳定 190–200ms（173/218）。若收尾余量后仍有轻微不顺，
下一步给档位判定加滞回（30m ± 3m），不要继续动前视/贴地。

## 4. 实机复测点与判据

- 复测点：① 台阶段（东侧 3→6、西侧 13→17、南侧 9→11）是否还有「入地→拉起」；② 平地/长直线段

  航点**（不再出现「最后包距航点 ~0.24m 后静默 ~1m」），且**距航点 ≤0.75m 后不再有流式包**
