# 任务 1922/2947 同形候选排查（29 项）

日期：2026-09-14

## 结论

上一轮审计留下的 29 个 `EVIDENCE_REQUIRED` 候选，本轮逐条取证完毕：

- 29 个候选（29 个任务，各 1 个物品）全部是“物品在接任务时就进入玩家背包”的交换型任务，不是 1922/2947 那种“任务中途掉落、完成时可有可无”的工作物品。
- 其中 26 个来自 retail `item_order` 模板，3 个来自 `data_driven_quest` 的 `start_give_item_id`。
- 25 个任务的客户端 `quest_summary` 明确写着“把 X 交给 / 拿给 Y”，属于必须交付物；完成时正数扣除就是正确合同，套用 2947 的 `count="ALL"` 会让玩家不交物也能领奖。
- 因此本轮判定：**29/29 均不属于 1922/2947 同类缺陷，不做批量替换**。
- 但发现一个独立缺口：这 29 条完成路由用正数 `remove-item` 卡住完成，却没有配套 `has-item` 条件；玩家丢物后点击领奖会静默无响应（和 1922/2947 的表现相同，成因不同）。若要修，方向是补显式守卫/客户端可见的拒绝，而不是放宽扣物。

本轮按指示**先不加固**：未改任何 quest XML、未改 Java、未加 CI 门禁或白名单。

## 扫描口径

全量扫描 `quest_definition/quests/*.xml`：与 `complete-quest` 同事务、带有正数 `remove-item`、且该物品在 `metadata/items` 中声明、且没有 `has-item` 守卫的完成路由，共 46 条路由 / 36 个物品 / 31 个任务。

- 其中 7 个物品的任务在 `origin/history` 里有旧 handler（11031、11032、2392 的 3 个物品、30003、30103），单列为“额外发现”。
- 剩余 29 个物品对应 29 个任务，即上一轮标记的 `EVIDENCE_REQUIRED` 集合，也是本轮的排查对象。

## plan 级探针

用 `QuestMutationPlanner` 直接对每条完成路由做两种背包状态的可行性判定（脚本为本轮一次性探针，已删除）：

```
29/29：hasItem=0 -> BLOCKED，hasItem=1 -> PLAN（removes 均为 count=1）
```

即这 29 条完成路由的可行性完全由“是否持有该物品”决定，符合“必须交付”的判定；同时说明它们在无官方 `has-item` 条件的情况下也会静默失败。29 个物品的模板动作只有 `queststart` / `read` / 空，没有消耗型动作，不存在“使用即消耗、完成再扣”的双扣死锁。

## 额外发现（不在 29 项内）

1. 任务 2392 `Beautiful Feather`：`started -> rN` 用 `has-item` + `remove-item count=1` 消耗掉分支物品，随后 `rN -> complete` 又要求同时扣掉 182204159/160/161 各 1 个。链式探针结果：进入领奖 `PLAN` -> 背包该物品归 0 -> 完成 `BLOCKED`（3 个分支全部如此），完成路由即使带着 1 个物品也 `BLOCKED`（三条同时要求）。旧 handler 在 REWARD 只做尽力扣除后直接 `sendQuestEndDialog`，说明这是引擎迁移后的**确定性卡完成**，优先级高于 1922/2947 当时的情况。
2. 任务 30003 / 30103：完成路由同样 `BLOCKED`(空) / `PLAN`(持有)，旧 handler 是在 REWARD 无条件 `removeQuestItem(...)` 后 `sendQuestEndDialog`（非条件判断）。上一轮记录里“旧 handler 明确扣除、属既有合同”的表述不准确，应按“旧引擎尽力扣除、新引擎硬门禁”重新取证。
3. 任务 11031 / 11032：物品在接取时发放，使用（`skilluse` 菜品）推进到领奖，完成路由再扣 1。旧 handler 完成时不校验物品。这两条需要单独确认“使用菜品是否消耗物品”，若消耗则同样是确定性卡完成。

上述三项均未修改，待后续单独授权。
